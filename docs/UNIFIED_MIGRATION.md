# Task and application migration

Source: LocalWake/UnlockTime 0.4.0, versionCode 11. Target: UnlockTime Unified 0.5.0, versionCode 12. The source workspace and rollback APK are preserved separately. Runtime authority is `routine-migration/authority-v1.json` under noBackupFilesDir; unified routine storage is versioned separately from old preferences.

The initial legacy owner remains sole authority during shadow comparison. A shared migration lease, execution mutex and legacy scheduling mutex stop work crossing cutover. The migrator takes a local tasks/history/guard backup (never credentials), stages the target, verifies every field, reopens the file and compares future occurrence times. Only after cancelling old alarms does a durable authority commit grant the new RoutineSystem execution. Every receiver verifies authority/epoch; stale broadcasts cannot claim a second attempt.

Preserved semantics include 32 tasks, 5 applications per sequence, repeated packages, ordering, millisecond waits before each application including the first, 30 seconds total waits, one-off absolute timestamps, weekdays, DST/timezone behavior, 10 minute lateness, enabled state, revision/token, history, unknown IN_PROGRESS outcomes and global authentication pause. WAKE_ONLY and INSPECT_GRID remain diagnostic modes, never upgraded to FULL. New deterministic OpenAppsSequence does not call a model.

ScheduleRepository becomes a compatibility facade over the committed unified store. Its original persisted bytes remain the migration source/backup; the legacy scheduler cannot create new executable alarms after cutover. The unified editor owns new and migrated tasks. Original credentials, compatibility records and app language preference remain in their original stores.

Interruption checkpoints are tested by reconstructing runtime objects from files. A damaged or contradictory journal assigns NONE, stopping both engines. A retry button invokes verified recovery with the same locks. Recovery after cutover retains newer history, deleted/changed tasks and failure guards; it only rebinds valid pending occurrences to a new epoch. Missing provenance or damaged target needs repair and cannot be solved by clearing data or blindly restoring a stale backup.

The old independently installed `com.phoneuse` application is a different sandbox. Its accounts, conversations and API keys are not copied from private storage. Users log in/configure their chosen provider inside the unified `org.localwake.app` application. Local integration does not require installing or launching the second APK.

Before installation, compare the target, build11 and phone-installed APK certificate SHA-256 with `dc14ee3a5c1795a62a15f22460db0fed05c3e66729496b57c6160c46b503b4e9`. On mismatch stop; never uninstall or clear data to force installation. A production data-preservation claim requires an actual same-signature update and post-update local readiness/task verification. Refer to the test report for what was actually exercised.

## Observed installation and restoration — 2026-11-16

The original build11, installed-before APK and unified candidate signing certificates matched. In-place replacement succeeded without uninstalling or clearing app data. The original source task-store hash was unchanged. A status-only test reported stored credential READY/PATTERN (no credential contents exported), both original task definitions/runtime fields and history preserved, migration identity/map matched, ROUTINE_ACTIVE epoch2 and the failure guard unchanged. Instrumentation itself interrupted the accessibility service; one normal Android settings re-enable restored it. Subsequent app-based tests established actual local pattern authentication and model-backed device operation. See the test report for checkpoint-specific details.

The final validation13 update retained the user's later-created routines and provider login. For the user's requested end-to-end trial, the same two existing daily routines were rescheduled through the normal UI, not replaced. Both alarm occurrences completed. Original daily times, enabled state, 60-minute cooldown and original prompt hashes were then restored and compared. Each routine has a fresh pending occurrence for the original time later the same day; old test tokens remain consumed. The final failure guard is false. This is an observed restoration, not a claim that rollback or every process-death transition has been tested on this phone.
